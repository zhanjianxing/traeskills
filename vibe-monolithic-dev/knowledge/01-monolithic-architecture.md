# 单体架构设计

## 一、架构概述

### 1.1 什么是单体架构

单体架构（Monolithic Architecture）是一种将所有功能集成在一个独立部署单元中的软件架构模式。与微服务不同，单体应用的所有模块共享同一个进程和数据库，通过内部方法调用进行通信。

### 1.2 单体架构的优势

- **开发简单**：单一代码库，易于理解和调试
- **部署简单**：单个JAR/WAR包，部署成本低
- **性能优势**：无网络延迟，事务处理简单
- **运维简单**：单一部署单元，问题定位容易

### 1.3 何时选择单体架构

- 团队规模 < 10人
- 项目周期短，需要快速交付
- 业务边界不清晰，可能频繁变化
- 不需要高并发、高可用特性
- 初期创业项目，后期可能拆分

## 二、模块化单体架构

### 2.1 核心理念

**空壳Server + 业务模块化**：
- Server工程：负责启动、配置、模块装配，是唯一部署单元
- 业务模块：按领域划分，封装业务能力，以依赖方式存在

### 2.2 模块划分原则

1. **领域驱动**：按业务领域划分模块（订单、商品、用户）
2. **高内聚低耦合**：模块内代码高度内聚，模块间通过接口通信
3. **单向依赖**：禁止循环依赖
4. **边界清晰**：模块有明确的职责边界

### 2.3 模块类型

| 模块类型 | 说明 | 示例 |
|----------|------|------|
| 公共模块 | 提供通用能力 | common-core, common-redis |
| 系统模块 | 提供基础能力 | system, infra |
| 业务模块 | 实现业务功能 | order, product, user |

## 三、项目结构设计

### 3.1 顶层结构

```
project/
├── pom.xml
├── server/                    # 启动入口
├── common/                   # 公共模块
└── modules/                  # 业务模块
```

### 3.2 Server工程职责

- 提供唯一启动类
- 管理依赖版本
- 集中配置管理
- 打包部署

### 3.3 公共模块职责

| 模块 | 职责 |
|------|------|
| common-core | 常量、异常、工具类、枚举 |
| common-redis | Redis配置、缓存操作 |
| common-security | 安全认证、权限校验 |
| common-web | 全局拦截器、参数解析 |

### 3.4 业务模块结构

```
module-xxx/
├── controller/      # 接口层
├── service/         # 业务层
├── repository/      # 数据层
├── dto/             # 数据传输对象
├── vo/              # 视图对象
├── enums/           # 枚举
└── convert/         # 转换器
```

## 四、分层架构

### 4.1 标准四层架构

```
┌─────────────────────┐
│   Controller层      │  接收请求、参数校验、结果封装
├─────────────────────┤
│   Service层         │  业务逻辑、事务管理
├─────────────────────┤
│   Repository层      │  数据访问、缓存操作
├─────────────────────┤
│   Entity层          │  数据模型、ORM映射
└─────────────────────┘
```

### 4.2 各层职责

**Controller层**：
- 接收HTTP请求
- 参数校验
- 调用Service
- 封装响应

**Service层**：
- 业务逻辑处理
- 事务管理
- 缓存操作
- 事件发布

**Repository层**：
- 数据库操作
- MyBatis映射
- 缓存读写

**Entity层**：
- 数据模型定义
- 表映射关系

## 六、部署架构

### 6.1 单机部署

适用于开发、测试环境：
- 应用 + MySQL + Redis 部署在同一服务器
- 使用Nginx反向代理

### 6.2 分布式部署

适用于生产环境：
- 应用多实例部署（负载均衡）
- MySQL主从分离
- Redis集群或哨兵模式

## 七、演进策略

### 7.1 何时考虑拆分

- 团队规模超过10人
- 业务复杂度增加
- 需要独立扩展特定功能
- 部署频率冲突

### 7.2 拆分策略

1. **独立公共模块**：将 common 模块拆为独立 Maven 依赖
2. **提取服务模块**：将业务模块拆为独立服务
3. **数据库拆分**：按模块拆分数据库

### 7.3 模块化单体优势

模块化单体架构可以在不改变部署结构的情况下：
- 按模块独立开发
- 按模块独立测试
- 未来平滑演进到微服务
